# 实测基线：制冰机 ASIN 的一次完整跑（2026-10-08）

> 用途：**跑完拿这份对一遍**。数字量级对不上，多半是哪一步参数或解析出了问题。

---

## 完整命令（可直接复制改 ASIN）

```bash
cd <工作目录>
export TYPESAFE_API_KEY=***                      # 换成你自己的 TypeSafe key
export AMZ_PROXY=http://<你的代理>:<端口>          # 直连不通时必设

python3 run_pipeline.py \
  --asin B0BWHZJHPL \
  --keywords "countertop ice maker,nugget ice maker,portable ice maker,bullet ice maker,ice maker machine" \
  --bsr-pages 2 --search-pages 5 --enrich 120 \
  --min-delay 5 --max-delay 8 --max-requests 400 --out out
```

依赖：`httpx` `beautifulsoup4` `lxml` `openpyxl`。

## 怎么判断这次跑「不对劲」

| 症状 | 大概率原因 |
|---|---|
| 搜索页解析出 **0 条**，或页面缓存 < 60KB | `bm-verify` 软验证页（不是选择器错） |
| 软验证次数 > 0 | 没走持久连接 / 没做首页预热 |
| 价格出现 4 位数「美金」（如 `$5143`） | 美元「分」单位没除 100 |
| 价格是 `S$` 等非美元 | `i18n-prefs=USD` cookie 没带上 |
| 打分**全部 ≥9** | 目标产品描述或问题设计有问题（判别力消失了） |
| 候选池 ≈ 原始命中数（几乎没去重） | 关键词太少或太同义（本次 5 词互不重叠才得到 55% 重复率） |
| 详情补全的比例看起来很低 | **算法原因，不是 bug** —— 见下 |

### ⚠️ 补全率是瓶颈，且这是设计使然

`--enrich 120` 只补**排序前 120 个**（排序键：出现频次 ↓ → 最好位次 ↑ → BSR 命中优先）。
本次池子 272 个，所以**有 152 个候选没补详情**，它们的 `brand` / `category` / `bullets` 为空，
打分只基于标题。

⇒ 想让全池都有详情：把 `--enrich` 提到 ≥ 池子大小（代价：请求数线性上涨，**有被封风险**）。
⇒ **默认不值当**：出现在多个词、多个页面的（高频次）本来就更可能是真对手，
按频次排序补全，把预算花在最该花的地方。

### 其他已知畸形数据（正常现象，别当 bug 修）

- **仅来自 BSR 的候选**（`best_pos` 会显示为 `仅BSR`）：本次 52 个。
  这些是搜索页完全没命中的，往往是自然排名稳但不投广告的老对手 —— 是**有价值的补充**，不是噪声。
- **价格区间跨到 `$3,100–$9,450`**：同属 `Ice Makers` 类目的**商用机**（Hoshizaki / Manitowoc）。
  它们是「类目相同 ≠ 竞品相同」的活证据，会被正确判成 `同类不同款`。
- **`同品牌家族` 混在池子里**：本次 11 个是自家品牌的其他型号。**不要过滤掉** ——
  它们确实在抢流量，只是属于「内部抢位」，需要单独处理。
